# 平台软件架构与驱动设计（V1.9.1）

> **规范性：** 本文件定义当前平台/驱动/启动/构建实现边界；板级事实以真实 `.ioc`、原理图和 07 号唯一资源表为准。


## 0. Flight 项目目录与现有工程接入

### 0.1 三层源码与命名

| 层 | 职责 |
|---|---|
| `sensor_device/` | 设备、总线事务、硬件时钟与采集缓冲。 |
| `middleware/` | 协议、传感器语义、导航、FMS、制导、控制和输出守卫。 |
| `applications/` | `main.c`、`tasks/` 和 `runtime/`，负责生命周期、调度和跨任务数据。现行线程见 07 §2.1.1。 |

- 自有源码和头文件用小写下划线，无 `fc_` 通用前缀。按功能建目录，C/H 放在一起。传感器目录用类别名，文件用具体器件名。存储目录使用 `W25Q64` 和 `SDMMC`。
- 模型名用于 `middleware/model/` 中对应实现。INS、FMS、Control、Plant 各有一组 `<module>_interface.c/.h`。开发者在构建清单中绑定唯一实现。内外环分别维护并成套选入，模型专用库、生成件、工具和许可证归该实现。
- 硬件访问由具体驱动通过 RT-Thread 原生设备或总线接口实现。M1、M2、M7 在适配处调用设备，应用消费中间层接口，协议解码不依赖设备或 RTOS。
- `board/` 负责板级绑定、时钟、引脚、DMA 和诊断。共享 HAL/CMSIS 包放 `packages/`，CORE 参数放根 `config/`，验收和官方资料分别在 `tests/` 与 `doc/`。

目录导航见 [工程目录](../PROJECT_STRUCTURE.md)。任务描述符、入口和周期常量按职责统一命名，例如 `task_sensor`、`task_sensor_entry` 和 `TASK_SENSOR_PERIOD_MS`。

### 0.3 构建与配置

固件由根 `SConstruct`、`SConscript` 和 Kconfig 构建，`.config` 与 `rtconfig.h` 同步。准确源集由各层 `SConscript` 维护，工程对象和栈报告按源路径进入 `build/`。

| 构建边界 | 门控与来源 |
|---|---|
| 板级与器件 | `board/SConscript` 和 `sensor_device/SConscript` 选择 BSP、传感器、DShot、NOR 和 SDMMC。 |
| 应用与中间层 | `FLIGHT_RUNTIME_ENABLE` 接入常规任务并选择 M2～M6。模型和专用后端由 `middleware/model/SConscript` 绑定。 |
| 仿真与板上用例 | `FLIGHT_SIM_LINK` 接入 `task_sim`、HIL 串口与协议，`FLIGHT_TARGET_UTEST` 接入 `tests/target/`。 |
| 飞行记录 | `FLIGHT_LOGGER_ENABLE` 接入 `task_logger`，依赖 SDMMC 和 RT-Thread DFS v1/Elm FatFs。 |

`rtconfig.py` 默认 GNU Arm Release（Cortex-M7、hard-float、fpv5-d16），支持 `RTT_EXEC_PATH` 与 `RTT_BUILD`。运行时与 INS 后端要求 GNU Arm。C/C++ 采用 C99/C++14，统一使用 `-fno-short-enums`，C++ 禁用异常、RTTI 和线程安全局部静态初始化。Flash 与 RAM 预算见 07。

日志使用 RT-Thread ulog，板上用例由 FinSH 手动运行 utest。普通任务 FIFO 使用静态 RT-Thread 消息队列并按各自策略处理溢出。快照在互斥边界复制，计算在临界区外执行，DMA 槽归驱动。

### 0.4 官方资料使用与驱动适配顺序

优先查阅项目已有资料：[硬件输入](../doc/Flight.xlsx)、[ADIS16505](../doc/ADIS16505/adis16505.pdf)、[ADI no-OS 器件实现](../doc/ADIS16505/no-OS/drivers/imu/adis1650x.c)、[ADI 官方用例](../doc/ADIS16505/no-OS/projects/eval-adis1650x/)、[BMM350](../doc/BMM350/BMM350.pdf)、[BMP585](../doc/BMP585/bst-bmp585-ds003.pdf)。引用具体版本/页码/函数、寄存器时序和配置读回，不因示例存在就认定目标配置通过。

设备接入按“检查现有驱动与配置 → 复用官方器件通用逻辑 → 适配现有 RT-Thread bus/device → 补齐板级挂接 → 验证”执行。官方 no-OS 的 STM32 平台、CubeMX 生成器、启动文件、main、调度和中断实现不整体移植；器件专用的可复用原厂源码内联进该器件的驱动文件（保留许可证与上游来源记录），板级共享第三方包仍归 `packages/`，适配回调调用本工程已有总线接口。总线事务/设备寄存器逻辑归驱动，样本单位/标定/安装旋转归 M2，边界按 02/05，不重复实现。

现有 `drv_spi.c`、`drv_hard_i2c.c`、`drv_usart.c` / `drv_usart_v2.c`、`drv_wdt.c`、`drv_crypto.c`、`drv_tim.c`、`drv_pwm.c`、DMA helper 和 RT-Thread 设备类是复用入口。驱动由现有 Kconfig 和构建条件选择，每个外设实例、IRQ 和 DMA 通道只有一个所有者。现有外设缺少高频异步能力时，在对应驱动内增加有界扩展。CubeMX、`board.c` 和 `board_device.h` 提供板级初始化和资源绑定，设备生命周期由现有 RT-Thread 框架管理。项目专用向量与设备实现放在一起。

## 1. PLATFORM / HEALTH & DIAGNOSTICS

### 1. 职责

PLATFORM 提供 BSP、时钟、RTOS 适配、原生设备驱动、DMA/IRQ/Cache、固定缓冲、参数、日志、看门狗和资源监控。HEALTH 汇总各模块发布的健康/故障证据、历史和资源统计，并向 M4 提供摘要。

HEALTH 不重复实现 M2 数据质量算法、M3 创新检验、M7 执行器诊断，也不决定返航/停车等操作。

### 2. Sensor Integrity Manager

Sensor Integrity Manager 是 HEALTH 中的传感器完整性子服务，唯一拥有 SensorHealthState、SensorUsePolicy、源级隔离和恢复状态。它汇总 PLATFORM 采集故障、M2 SensorDiagnostic 和设备自检证据。M3的`EstimatorHealth`/`NavigationCapability`可作为导航质量的汇总证据，但不能单独触发某个传感器源级隔离；Sensor Integrity Manager必须结合M2设备/样本级证据和多源证据，且不得读取KF-GINS插件私有残差/协方差。EstimatorPort内部诊断保持插件私有。

它不修改 M3 状态、不改变滤波器内部参数、不做 FMS 操作决策。输出 SensorUsePolicy 给 M3，FaultSummary 给 M4。

### 3. 故障所有权

- 传感器链路/设备质量：PLATFORM/M2 发现证据。
- 单次观测创新/一致性：M3 处理。
- 传感器源级隔离/恢复：Sensor Integrity Manager。
- 操作级响应：M4。
- 控制可控性：M6。
- 执行器本地故障/输出保护：M7。
- RTOS/CPU/RAM/clock/stack：PLATFORM Health。

### 4. 实时性

健康统计、故障历史写入和日志不得阻塞高频控制/IMU 路径。高优先级事件采用有界队列和明确溢出策略；低优先级日志可丢弃，但安全事件必须保留计数/锁存状态。

### M3 KF-GINS固件集成边界（V1.9.1现行）

- KF-GINS算法内核由B维护，采用C++14静态编译目标；对外只通过02号ICD的C-compatible EstimatorPort导出函数，不改变RT-Thread Device Framework或平台设备生命周期。
- A负责提供原始驱动样本/字节流、DRDY/PPS硬件捕获时间、DMA状态和底层设备诊断；B负责M2语义适配（传感器帧/协议语义解析、单位转换、标定、安装旋转、group-delay/sample-time修正、质量标志），生成02号ICD定义的标准化ImuSample、GnssSample、BaroSample、MagSample；B负责M3滤波观测模型。
- H723固件不链接KF-GINS桌面入口、fileloader/filesaver、YAML解析、命令行、控制台输出或不必要第三方依赖；配置由Host校验后生成静态只读头文件。
- 固件侧禁止运行期heap、异常、RTTI和动态矩阵resize；所有KF-GINS工作区固定维数、静态分配。C++全局静态初始化必须审查，EstimatorPort生命周期显式初始化。
- A负责C++工具链/链接脚本/浮点ABI与RTOS集成验证；B负责算法适配和数值测试；A维护平台依赖锁，B固定KF-GINS输入，D汇总License/SBOM并独立审查。

### Time Service与GNSS故障隔离（V1.9.1现行平台契约）

PLATFORM Time Service是本地时间和外部时间映射的唯一Owner。它独立发布`TimeServiceStatus`、`TIME_BASE_FAULT`、`PPS_LOST`、`UTC_EPOCH_INVALID`和`TIME_MAPPING_DEGRADED`。

- GNSS SensorHealth只表示GNSS设备/观测源状态；Time Service状态只表示本地时钟与外部时间映射状态。
- UM982是当前产品必装主要器件；GNSS初始化/通信失败必须进入相应设备故障统计，不能伪装成GNSS_NOT_INSTALLED。
- GNSS丢失不得将本地Clock Service置为FAILED；TIM2仍持续计数和捕获IMU DRDY。
- 只有TIM2停摆、RCC时钟异常/切换未校准、扩展歧义或本地时钟不连续才触发TIME_BASE_FAULT。
- RTC、TCXO和Companion时钟映射由PLATFORM统一管理；M1/M2/M3不得维护各自私有UTC offset/drift。

### 5. RT-Thread v5.3.0 配置原则

#### 5.1 内核与基础组件

按需启用内核线程调度、时钟/定时器、必要 IPC、内存管理和 I/O Device
管理。按实际硬件启用 SPI、I2C、Serial、CAN、PWM、ADC、Watchdog
等驱动子框架。文件系统/DFS、网络协议栈、LWP、图形界面和不使用的中间件默认关闭。FinSH/MSH
仅在开发/维护构建启用；量产构建必须关闭或通过维护授权严格限制。

每个启用组件必须登记使用者、Kconfig 选项、静态/动态
RAM、线程数、优先级、是否进入实时路径和验收证据。禁止为追求"功能完整"而无差别开启全部组件。

#### 5.2 RTOS Adapter

业务模块只能调用项目 API。建议最小接口集合：

-   `os_task_create_static()` / `os_task_start()`；
-   `os_notify_from_isr()` / `os_event_wait()`；
-   `os_sem_take()` / `os_sem_give()`；
-   `os_mutex_lock_timeout()` / `os_mutex_unlock()`；
-   `os_delay_until()`；
-   `os_critical_enter()` / `os_critical_exit()`；
-   `os_get_task_stats()` / `os_get_stack_watermark()`；
-   `clock_now_us()` 由 Clock Service 提供，不把 RTOS tick
    暴露给算法。

以上为项目接口命名建议，最终原型、返回码和上下文限制由代码头文件与 ICD
配套冻结。所有 ISR 版本 API 必须标注允许的 IRQ 优先级范围。

#### 5.3 线程与优先级

线程优先级不能在未测 WCET
前随意固定。每个线程必须给出触发方式、频率/最小到达间隔、deadline、WCET、最坏阻塞时间、stack
size、CPU budget、队列/ring 容量、超时和过载策略、watchdog 规则。

对 IMU ingest、M2 IMU processing、M3 INS prediction、M7 actuator output
等关键任务执行响应时间分析。优先级以
deadline、阻塞和依赖关系确定，不以模块编号决定。

#### 5.4 ISR 规则

-   ISR 只确认中断、锁存硬件时间、管理 DMA
    状态、提交固定描述符和触发允许的通知。
-   ISR
    不做传感器业务解析、滤波、矩阵计算、动态内存分配、日志格式化或阻塞操作。
-   NVIC 优先级 0–3 的 ISR 禁止调用 RTOS API；优先级 4–12 仅允许经验证的 ISR-safe notify/semaphore/event API，具体见07号文档的实时资源基线章节。
-   不得套用 FreeRTOS `configMAX_SYSCALL_INTERRUPT_PRIORITY` 规则。RT-Thread v5.3.0 Cortex-M7 端口的全局中断关闭使用 PRIMASK/CPSID I，所有可配置 IRQ 都可能被短临界区屏蔽；必须测量并限制临界区时间。
-   IRQ priority grouping、实际 IRQn 和优先级由 BSP 单一配置源管理；功能级优先级表见07号文档。

### 6. 启动与初始化顺序

1.  Reset/Startup：向量表、栈、data/bss、FPU。
2.  BSP early init：时钟树、MPU、Cache、基础 GPIO、硬件安全默认态。
3.  Resource Registry：注册 pin/EXTI/DMA/IRQ/Timer/PWM/Bus 资源。
4.  RT-Thread kernel：内核和调度器启动。
5.  RTOS Adapter：初始化 OS 抽象。
6.  Clock/Time Service：建立单调高分辨率时间源。
7.  HAL/Bus：初始化实际使用的外设总线。
8.  RT-Thread原生Device Framework与具体设备驱动实例：注册总线和设备。
9.  DMA/Buffer/Acquisition：建立 DMA pool、descriptor、raw ingress ring
    和采集任务。
10. Parameter/Logger/Watchdog/HEALTH/FDIR/Message Bus。
11. M1～M7 模块初始化并完成自检。
12. System Readiness：发布系统能力；FMS 评估是否允许进入可解锁状态。

#### 6.1 Bootloader 与固件生命周期（V1.9.1唯一流程）

首版`BOOT_MODE=DIRECT_BSP`：复用当前启动文件和linker，不包含已实现的签名升级/自动回滚承诺；在线升级接口返回UNSUPPORTED。启动为RESET→BSP_INIT→SELF_TEST→READY或FAULT_INHIBITED。缺少Bootloader分区、密钥与双镜像容量证据时不得配置安全升级能力。

后续`VERIFIED_AB_BOOT`必须单独完成分区/镜像容量/签名密钥/防回滚/掉电Recovery设计与CR；其状态为RESET→VERIFY→TRIAL→CONFIRMED，失败ROLLBACK/RECOVERY。W25Q64现有Reserved区未分配镜像槽，不得默认挪用；升级暂存与last-known-good必须有独立完整容量。该可选模式目前FEATURE_DISABLED，不能作为首版可恢复性依据。

关键初始化失败必须产生结构化 FaultEvent，并阻止依赖该能力的模式启用。Watchdog 只能由 Supervisor 在检查关键任务心跳、deadline miss、栈/资源故障和系统健康后喂狗；禁止由无条件周期定时器喂狗。禁止以“启动继续”掩盖关键硬件未初始化。

#### FPU ABI 与 RTOS 上下文契约

所有 Cortex-M7 浮点目标文件、静态库和最终固件必须使用一致的浮点 ABI；QUAD H723 候选编译目标为 `-mfpu=fpv5-d16 -mfloat-abi=hard`，最终以实际 GCC/ABI 构建日志为证据。RTOS 端口必须证明线程切换时保存/恢复浮点上下文，覆盖 S0–S31/FPSCR 所需状态及 lazy stacking/异常嵌套行为；不能仅以 CPACR 已开启作为通过依据。ISR 禁止执行浮点算法。实际 RT-Thread 配置宏、端口实现和编译选项必须从锁定源码核验，当前依赖锁缺失，保持 `SOURCE_EVIDENCE_PENDING`。

#### MPU/D-Cache 配置证据

MPU region 表、Cacheable/Non-cacheable 属性、Shareability、execute permission、DMA master 可达性必须在 BSP 初始化、Linker Script 和 07 内存表之间一致。Cortex-M7 D-Cache line 按 32 B 对齐；DMA RX/TX 的 clean/invalidate 顺序和 DMB/DSB 屏障按具体驱动契约实现；DMA buffer 不得与普通变量共享 cache line。目标 MPU 配置、RAM remap 和 Cache stress test 未提供前不得标记通过。

### 7. 内存、Cache 和资源规则

本节为平台级原则摘要；驱动侧 DMA buffer 所有权、对齐和维护操作见本文件第 3 章第 5 节，具体 SRAM 区域与容量见 07 号文件。两处不得分别维护不同的 Cache 策略。

-   高频实时任务栈、DMA buffer、descriptor、SPSC ring
    和控制数据使用静态分配或固定容量池。
-   动态堆仅用于启动期/低优先级非实时任务；运行期监控堆水位和分配失败。
-   DMA buffer 必须位于 DMA master 可访问的 SRAM 区域；不得默认把
    DTCM/任意 RAM 都视为 DMA 可访问。
-   Cortex-M7 D-Cache line 对齐；优先使用专用 MPU non-cacheable DMA
    区域，或按 DMA RX/TX 方向实现正确 cache maintenance。
-   DMA RX 在 DMA 前处理脏 cache line，DMA 完成后 CPU 读取前
    invalidate；DMA TX 在启动前 clean；cache line 不得与非 DMA
    数据共享。
-   Resource Registry 必须防止两个驱动重复使用同一 DMA
    stream/channel、Timer channel、引脚或 IRQ。

### 8. 系统服务策略

-   Message Bus：命令/故障事件可靠有界；状态快照 latest-value；高频 IMU
    专用 ring；日志低优先级队列。
-   Parameter Manager：参数有 ID、类型、单位、范围、默认值、版本、CRC
    和生效条件。
-   Logger：实时任务只写固定记录到有界队列；后台任务写存储。
-   Watchdog：关键任务 heartbeat/deadline 全部满足才允许喂硬件狗；logger
    不得单独喂狗。
-   HEALTH：收集故障历史和资源指标，不成为实时保护唯一执行者。
-   Sensor Integrity Manager（HEALTH 子服务）维护传感器源级健康状态和 SensorUsePolicy；M4 选定的车辆 FMS Policy 做操作级决策。

#### 8.2 通信职责边界

- M1 RC Adapter只解析接收机帧、归一化OperatorInput、维护链路状态；不决定飞行模式、不授予Authority。
- M1 MAVLink Gateway负责MAVLink 2 framing/parser、CRC、签名/来源认证、Source/Target、序号/防重放、TTL、白名单和OperationRequest转换。
- M4是所有外部命令的唯一权限仲裁入口；MAVSDK、QGC、MAVProxy和Companion均不能绕过M4写M6/M7。
- MAVSDK是地面端/Companion高层客户端；MAVProxy是地面/伴随主机侧路由器，不进入FCU实时闭环。
- Companion只提交已验证的环境/路径建议；其USART1占位接口关闭时，基础飞行功能必须独立运行。

#### 8.3 存储服务边界

SDMMC1 和 OCTOSPI NOR 由各自的原生设备驱动维护。`task_logger` 独占 SD/FatFs 会话，通过共享快照和有界事件队列记录飞行数据。计划由 `task_flash` 独占 NOR 会话，保存关键事件与 A/B 非安全设置，见 07 §7.1。控制、采集与监督路径不等待存储。

W25Q64逻辑分区和SD目录唯一见07号文件第7章存储章节；Flight.xlsx保持本次硬件输入原样；逻辑地址/软件事务只由07/08维护，目标工程源证据经CR追溯。四份核心工程调参只以构建生成的.rodata和core_parameter_hash生效，W25Q64不覆盖核心参数。A/B journal唯一保存08白名单的NonSafetySettings；SD CONFIG_MIRROR仅为导出备份，启动不得自动回灌。固件核心参数变更必须重编译/重新验证。

#### 8.4 生产构建约束

- 量产Profile关闭FinSH/MSH；若USART1选择Companion，Debug Adapter必须关闭。
- UART TX采用DMA/非阻塞队列；实时任务不得等待发送完成。
- RX DMA采用有界环形缓冲，HT/TC/IDLE/错误事件统一更新生产者位置；不得仅依赖IDLE判定帧边界。
- LinkMonitor分别维护RC/GCS/Companion状态；任何一条链路的heartbeat不得掩盖另一条链路失联。
- DMA buffer的Cache策略、可访问SRAM区域和对齐以07号文件和目标链接脚本为准。

## 3. 原生 RT-Thread 5.3.0 驱动与设备接入

### 1. 强制决议

**驱动框架必须使用 RT-Thread v5.3.0 原生 Device Framework 及其原生设备/总线子框架。禁止项目再造 `DeviceInstance`、`DeviceDriverOps`、统一 DriverManager、第二套设备注册/生命周期框架。**

项目必须先复用 `libraries/HAL_Drivers/`、`board/` 和 `rt-thread/components/drivers/` 的现有实现；只在有明确缺口时增加设备专用挂接或异步 DMA 扩展，遵循原生 `rt_device` 注册、设备类/总线、控制和生命周期。器件专用原厂源码内联进该器件的驱动文件，板级共享第三方包归 `packages/`，上层语义适配归 `middleware/`，落位见 §0.2；不重新生成驱动/BSP，上层不得直接操作 HAL/寄存器。

### 2. 驱动分层

```text
M1/M2/M7 business adapters
        |
RT-Thread native rt_device / native bus & device class framework
        |
Project concrete device driver (RT-Thread driver implementation)
        |
RT-Thread BSP + HAL (LL/register only with measured justification)
        |
STM32H723 peripherals / DMA / IRQ / Timer / SRAM
```

业务模块可拥有薄的类型适配函数，将 `rt_device` 读取结果转换成 ICD 强类型消息；这不是第二套驱动框架，不拥有设备注册和通用生命周期。

### 3. 原生框架使用规则

- 设备通过 RT-Thread 原生设备注册/查找/打开/关闭/控制接口管理。
- SPI/I2C/UART/CAN/PWM/ADC 等优先使用 RT-Thread 对应总线或设备类框架。
- 设备初始化、配置、诊断和生命周期遵循原生接口。
- 设备驱动明确并发、阻塞、超时、DMA cancel/close 收尾和资源 owner。
- 不复制一套通用 `probe/init/start/stop/deinit` 函数表包装所有设备。
- 若原生设备接口不足，采用该具体驱动的 `rt_device_control` 命令或设备专用扩展，不抽象成第二个全局框架。

### 4. 高频 IMU/执行器路径

高频路径不要求逐样本阻塞 `rt_device_read()`。具体 IMU 驱动内部可以使用 DRDY/FIFO、硬件捕获、SPI DMA、固定 DMA buffer、descriptor ring 和完成通知；但设备仍由原生 RT-Thread Device Framework 注册和管理。

ISR 只做最小有界工作：捕获时间/状态、提交 DMA 或确认中断、通知完成。不得在 ISR 解码、滤波、融合、分配内存或打印日志。DMA complete 后由高优先级 ingest worker 完成所有权转换并发布给 M2。

M7 通过原生 Timer/PWM/DShot/CAN 驱动确定性输出。若使用专用 DMA/定时器输出，扩展必须封装在具体 RT-Thread driver/BSP 中。

### 5. DMA/Cache/内存

- DMA buffer 位于对应 DMA master 可访问的 SRAM；DTCM/ITCM 不可默认 DMA 可访问。
- 按 Cache Line 对齐，优先 MPU non-cacheable 专用区；否则严格 clean/invalidate/barrier。
- DMA buffer 和普通变量不得共享 Cache Line。
- buffer 有明确 owner、generation、长度、sequence、sample timestamp 和状态；禁止重复归还/过期 descriptor。
- 传感器采样时刻、DRDY 捕获、DMA 完成和任务消费时间分别记录。

### 6. 驱动错误职责

驱动只报告硬件/总线/DMA/FIFO/设备错误证据，不决定传感器是否长期隔离或车辆是否返航。M2 做数据质量检查；Sensor Integrity Manager 做源级隔离；M4 做操作响应。

### 7. HAL/LL/寄存器

HAL 为默认；只有性能测量或功能缺口证明必要时，才在具体驱动/BSP 内使用 LL/寄存器。一个外设实例只有一个底层 owner，不允许 HAL 与 LL 两套实现竞争寄存器。业务层不得 include HAL/LL 头文件。

### 8. 驱动验收

设备身份/配置读回/self-test；bus timeout/NACK/CRC/DMA error/reset/断线；并发和 close 行为；IRQ/DMA 资源冲突；Cache 一致性；sample timestamp/sequence/data age；缓冲区越权/重复释放；M2/FDIR 故障链路。更换同类传感器时，M3 公共导航接口不变。

### 故障证据边界（V1.9.1现行规范）

原生 RT-Thread driver 负责返回设备/总线/IRQ/DMA/FIFO/复位事实和时间戳，不负责推断“风扰”或导航失效。驱动诊断必须区分硬件读写失败、数据路径丢样、设备自检错误和样本值超域。具体诊断事实通过 M2/平台健康适配层上报；不创建第二套 DriverManager、DeviceInstance 或 DeviceDriverOps。

### 本板设备资源绑定

项目 `doc/Flight.xlsx` 含“引脚”“接口配置”两个工作表，是板级设计清单核对基准；现有 `.ioc`、初始化和链接脚本的具体位置见 §0.1。文件存在不表示已经与原理图和目标板逐项核验。07的引脚/外设实例清单须与该工作簿逐项对照；软件位时序/缓冲等修正按07记录差异，不要求复制工作簿中的已知缺陷，并将未由源证据核验的项目标记 `SOURCE_EVIDENCE_PENDING`。仍然只使用RT-Thread v5.3.0原生Device Framework，不创建第二套驱动框架。设备驱动实现可使用其专属DMA/IRQ，但必须遵守07号文档中的板级资源唯一性表和RTOS ISR API约束。SDMMC1 internal IDMA、OCTOSPI1和TIM1 PWM外设本身不能误写成DMA1/2 Stream；TIM1更新事件可作为DMAMUX请求源，Flight.xlsx记录其通过DMA2_Stream2执行四路CCR Burst；RM0468/HAL静态映射确认`DMA_REQUEST_TIM1_UP=15U`可经DMAMUX1_Channel10路由至DMA2_Stream2，实际项目`.ioc`/生成代码仍须核验。

### 跨任务快照与异步总线的实现约束

所有跨任务latest快照使用双槽+pin元数据：发布索引为原子uint32；每槽原子pin_count及generation。读者最多两次执行“读取索引→短临界区校验索引/generation并pin”；取到后复制到消费者私有scratch，立即unpin，算法计算期间不占槽。写者只写非published且pin=0的槽，写完release发布；无空槽丢本次发布并计数/年龄告警。高优先级读者不循环等待写者，不使用会被高优先级抢占的低优先级seqlock写者；元数据临界区<2us，整包复制在临界区外。单写者由模块所有权保证，两个读者可同时pin同一published槽。generation不回绕；非零boot/epoch与TTL仍逐项校验。每通道20B管理元数据（发布索引4B、两槽pin/generation各8B）纳入07 ICD arena，内部实时环采用SPSC release/acquire，不把volatile当同步。

TIM2 DRDY ISR只能调用该具体SPI驱动已验证的`isr_submit_prearmed`路径（预建DMA、独占SPI1、无mutex/等待）；不可直接调用可能锁总线的`rt_spi_transfer`或HAL通用阻塞API。普通任务访问仍走现有RT-Thread SPI框架。改动点限定已有驱动的设备专用异步扩展，不引入第二套设备对象模型。

UART循环DMA采用HT/TC维护绝对生产计数，IDLE只补取当前位置；不能用NDTR相同判断“无新数据”。中断延迟跨越一个完整ring、overrun或计数不一致即清帧/记录丢失并重新同步，禁止拼接被覆盖帧。所有资源仍复用现有HAL_Drivers及board映射。

完整QUAD算法采用GCC C++14，当前可用STM32CubeCLT GCC14.3.1。通过既有SCons的`RTT_CC=gcc`/`RTT_EXEC_PATH`选择，application构建文件为C++目标加`-std=c++14 -fno-exceptions -fno-rtti`及统一hard-float；保留原BSP默认Keil设置，不把armcc默认构建当成Eigen/C++14已兼容。算法包版本在导入时锁完整commit/内容hash，`latest`不是可复现发布依赖。
