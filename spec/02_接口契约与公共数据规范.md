# 接口契约与公共数据规范（V1.9.1）

本章定义公共 ICD、Port 和 ABI。Schema 为 6.0，Product/Port Revision 为 **0x00010906**。生产头位于 `middleware/contracts/`，公共入口为 `ports/port_api.h`。导航私有状态和设备私有采集类型归实现模块，边界见 03 和 05。

## 1. 公共接口控制文件 ICD

### 1. 权威性

本文件是 M1-M7、HEALTH、PLATFORM 和模型适配器之间跨模块消息/端口数据类型的唯一权威来源。模块规范只能引用本文件，不得另行定义同名结构。`02_接口契约与公共数据规范.md`（可插拔接口章节） 规定如何绑定实现；本文件规定数据和调用契约。

### 2. 公共状态码

```c
typedef int32_t Status;
enum {
  STATUS_OK = 0,
  STATUS_INVALID_ARGUMENT = -1,
  STATUS_NOT_READY = -2,
  STATUS_OUT_OF_RANGE = -3,
  STATUS_UNSUPPORTED = -4,
  STATUS_NUMERIC_ERROR = -5,
  STATUS_DEADLINE_MISSED = -6,
  STATUS_PROFILE_MISMATCH = -7,
  STATUS_MODEL_OUT_OF_DOMAIN = -8,
  STATUS_BUFFER_FULL = -9,
  STATUS_STALE_DATA = -10,
  STATUS_NOT_PERMITTED = -11
};
```

错误码只表示本次调用/数据处理结果；长期健康状态通过 Health/Capability 消息报告。

### 3. 两层契约：公共 envelope + Product Contract

所有产品共享同一组 Port 名称、生命周期、公共消息头和基础语义。每个构建目标在 `product_contract.h` 中声明一套强类型 payload。实现按以下依赖顺序组织。QUAD_X4、UGV 和 USV 示例对应不同目标。

```text
base_types/common_base.h
  ├─ ContractHeader / common enums / common sensor sample types
  └─ NavStateCore / common diagnostics

product_contract/product_contract.h
  ├─ includes base_types/common_base.h
  └─ defines the target's Product* payloads as complete struct/union types

messages/common_messages.h
  ├─ includes base_types/common_base.h and product_contract/product_contract.h
  └─ defines messages containing Product* payloads by value

ports/port_api.h
  └─ includes the Port aggregates and declares stable module Ports
```

这些类型是编译期强类型，不是运行时任意 tag/void payload。每个产品编译时只包含自己的 payload 定义。公共 Port 的函数名称和语义保持稳定；不同产品的内部结构布局可以不同，因此每个产品固件有自己的 ABI/build manifest。跨设备网络协议必须独立序列化，禁止直接发送 C struct 内存镜像。

禁止：万能 `float data[32]`、跨模块 `void*` payload、未定义单位的数组、用 `layout_id` 猜测数组字段含义。数学模型内部允许编译期固定维数的向量/矩阵。

### 4. ContractHeader、时间和坐标

```c
#define CONTRACT_SCHEMA_MAJOR 6u
#define CONTRACT_SCHEMA_MINOR 0u
#define PORT_API_REVISION 0x00010906u

typedef struct {
  uint16_t schema_major;          /* V1.9.1 schema major 6 / minor 0: schema_major = 6 */
  uint16_t schema_minor;
  uint16_t message_type;
  uint16_t source_id;
  uint32_t sequence;
  uint32_t profile_id;
  uint32_t frame_id;
  uint64_t boot_id;                /* unique boot session identifier */

  uint32_t clock_domain_id;       /* domain of timestamp_sample_us; FCU monotonic */
  uint32_t time_epoch;             /* local FCU monotonic continuity epoch */
  uint32_t source_clock_domain_id; /* raw source domain; 0 for native FCU-timed source */
  uint32_t source_mapping_epoch;   /* mapping used to convert source time; 0 if native */

  uint64_t timestamp_sample_us;   /* converted event/sample epoch in FCU monotonic */
  uint64_t timestamp_publish_us;  /* FCU monotonic publication time */
  uint64_t valid_until_us;        /* FCU monotonic expiry */

  uint32_t event_time_uncertainty_us;
  uint8_t  timestamp_quality;     /* TimestampQuality, not global TimeQuality */
  uint8_t  timestamp_flags;
  uint16_t reserved;
  uint32_t validity_flags;
} ContractHeader;
```

- 内部所有控制/导航/任务期限使用本地单调64-bit微秒时钟；`timestamp_sample_us`永远不是UTC。
- `time_epoch`表示本地FCU单调时钟连续性epoch；TIM2复位、无法证明连续的时钟切换或MCU重新启动后变化。MCU重启同时生成新的`boot_id`；日志/跨重启回放必须使用`boot_id + time_epoch + monotonic`共同识别时间轴。
- `source_mapping_epoch`表示将该消息源时钟域换算到FCU单调时间时使用的映射epoch；本地硬件捕获源为0。
- `event_time_uncertainty_us`描述该sample/event时刻在FCU单调时间轴上的误差，不是UTC误差；UTC和其他外部时钟域的不确定度由对应ClockDomainMappingStatus给出。
- `timestamp_quality`使用TimestampQuality枚举描述单条消息时间戳来源质量；TimeServiceStatus.state使用TimeQuality描述UTC参考状态，两者不得混用。LOCAL_ONLY表示本地单调时间有效但没有可信UTC参考，不是系统故障。
- sample、hardware capture、DMA start/complete、SPI EOT、consume、publish是不同时间，不得互相替代。外部时间必须带source clock domain、source mapping epoch和uncertainty。
- 公共导航坐标采用局部 NED，机体采用 FRD，四元数 `[w,x,y,z]` 表示 body-FRD 到 nav-NED。非此约定的数据必须先显式转换。
- 单位：m、m/s、m/s²、rad、rad/s、N、N·m、kg、kg·m²；不得用裸数字表达物理量。
- 无效维度使用 valid mask；NaN/Inf 不得进入控制输出；零值不是无效标志。


#### 4.1 PLATFORM 时间与原始采集服务契约（规范性）

设备由驱动通过原生 RT-Thread 接口注册。IMU 采集适配读取 `imu` 设备时，`rt_device_read()` 将完整的 `struct imu_raw_sample` 复制到调用方缓冲。记录包含 32 B burst、硬件时钟 tick、序号和状态，定义归设备层 `sensor_device/imu/adis16505.h`。驱动独占 DMA 和原始队列，M2 将 capture tick 转换到当前 boot/time epoch 的单调微秒轴。

```c
typedef struct {
  uint64_t boot_id;
  uint64_t capture_ticks64;
  uint64_t capture_time_us;
  uint32_t time_epoch;
  uint32_t discipline_epoch;
  uint32_t edge_sequence;
  uint32_t event_time_uncertainty_us;
  uint16_t timer_instance;
  uint8_t channel;
  uint8_t flags;
} TimerCaptureEvent;
```

设备无可读记录时返回 0 字节，读取成功返回完整记录的字节数。驱动统计队列溢出，M2 按采集状态和序号接纳样本并更新健康状态。Timer ISR 只进行有界整数 tick 处理和事件记录。

#### 4.2 INS—CONTROL统一状态时间契约（规范性）

**核心原则：M3发布的是带测量/估计时刻的导航状态；M6必须在同一个控制计算时刻比较状态与参考。任务运行时刻、状态时刻、参考时刻和执行器生效时刻不得混为一谈。** 组合导航在本架构中的规范名称为“导航状态估计器（Navigation State Estimator，M3/Estimator）”；“观测器”可作为控制理论解释用语，但正式模块、文件、类型和任务名统一使用`Estimator/导航状态估计器`，不另设Observer模块。

统一时间术语：

| 规范名称 | 字段/定义 | 唯一含义 | 禁止替代项 |
|---|---|---|---|
| Measurement Time | `timestamp_sample_us` | 物理测量/事件在FCU monotonic轴上的时刻 | DMA完成、任务消费、发布时刻 |
| Arrival Time | `timestamp_arrival_us`（仅私有诊断） | 数据进入对应软件队列的时刻 | 物理测量时刻 |
| Publish Time | `timestamp_publish_us` | 模块发布快照的时刻 | 状态对应时刻 |
| State Time | `NavigationSnapshot.header.timestamp_sample_us` | `NavStateCore`所描述状态的参考时刻 | 当前读取快照的墙钟时刻 |
| Control Time | `ControllerInput.control_time_us` | 本次M6控制计算所采用的统一状态/参考评估时刻 | 任务唤醒时刻的无条件替代 |
| Reference Time | `MotionReference.header.timestamp_sample_us`及各点`offset_us` | 参考轨迹锚点及未来点时刻 | 参考消息发布时刻 |
| Actuation Apply Time | M6私有预测/延迟补偿参数 | 预计本次需求对PLANT开始生效的时刻 | Control Time |

**首版执行规则：**
1. M3的1kHz传播由有效IMU样本驱动；发布的`NavigationSnapshot`必须声明其`State Time`。M6快环以新鲜导航快照事件触发，`control_time_us`取本次控制计算选定的状态评估时刻，不取RTOS任务实际开始运行的时刻。
2. M6在一个控制周期内必须使用同一`control_time_us`评估导航状态和参考轨迹。`MotionReference`按其锚点和offset插值到该时刻；禁止直接拿“最新参考点”与“最新导航快照”相减。
3. 首版不允许M6自行修改或外推M3的导航状态。若`State Time`与`control_time_us`不相等，M6只能使用M3通过受控接口提供的、已标明目标时刻的状态快照；在该接口/预测模型未实现前，必须将`control_time_us`设为被选中`NavigationSnapshot`的`State Time`，并按数据年龄门限拒绝过期快照。不得在M6私自用常速度/常角速度外推冒充Estimator预测。
4. `timestamp_publish_us - State Time`是快照发布延迟；`control_time_us - State Time`是状态对齐间隔；两者必须分别测量和门控。M6还必须检查`time_epoch/boot_id/state_epoch/origin_id`与参考消息一致。
5. MPC 50Hz求解的初始状态、首个参考点和约束必须对齐到同一MPC评估时刻。MPC输出给1kHz快环时保留其`state_epoch/reference_epoch/authority_epoch/model_epoch`和有效期；快环不得等待MPC求解。MPC参考预览的执行延迟补偿`T_act`只用于参考预瞄，不得篡改导航State Time。`t_mpc_eval=control_time_us`，不使用RTOS任务开始运行时刻作预测锚点。
6. M7输出刷新时刻、DShot帧起始时刻和ESC实际作用时刻属于执行链时间；M7/PLATFORM记录这些时间用于端到端延迟分析。不得把输出帧时间回写成NavigationSnapshot时间。
7. 所有时间差计算必须先验证`boot_id`和`time_epoch`相同；跨epoch不允许做普通减法。时间戳倒退、未来时间超容差、时间不确定度超限或快照超过TTL时，M6拒绝该输入并发布`ControlHealth`原因；M4按能力与安全策略决定降级。

`ControllerInput.control_time_us`是所选NavigationSnapshot的State Time；`evaluation_time_us`是本次入口读取TimeService的当前monotonic时刻，用于TTL、age和deadline。二者在同一boot/time epoch内独立且不可互作别名，`evaluation_time_us >= control_time_us`。禁止保留含糊的now_us迁移字段。本接口于 0x00010905 首次明确区分两个时间字段（CR-V191-M45-01；Schema 6.0不变）；V1.9.0及更早公共布局不能混用。

契约规则：

- `PpsCaptureEvent`由PLATFORM/Timer Driver产生；只有Profile启用GNSS PPS时才有事件。事件必须携带扩展后的原始硬件tick，而不是任务到达时间或DMA完成时间。
- 有效GNSS PPS必须参与本地时间基准频率驯服：Time Service根据连续PPS原始tick间隔估计TIM2实际tick频率/频率误差，并对`raw_tick64 -> FCU_MONOTONIC_US`比例进行有界、连续的rate discipline；不得每秒清零TIM2 CNT，不得step/backward-jump已发布的monotonic时间。
- PPS与可信UTC历元配对后，另行更新`FCU_MONOTONIC -> UTC`的offset/rate映射。频率驯服与UTC绝对时间映射是两个独立结果：有效PPS但UTC历元无效时，可在接收机规格保证1 Hz脉冲可信的前提下校准本地频率，但`utc_valid`必须保持0。
- `clock_ticks_to_mono_us()`必须使用与事件`time_epoch`匹配的连续映射版本；历史捕获时间不得因后续rate更新而被追溯性改写。rate更新采用连续锚点和受限slew，跨版本转换需保留足够的mapping history。
- `LocalTimebaseDisciplineStatus`报告本地tick-to-monotonic频率驯服状态；`TimeServiceStatus`报告UTC参考状态。二者不得合并成一个LOCKED标志。
- `GnssTimeObservation`由GNSS解析适配器提供；必须显式携带时间尺度、接收机有效标志和与PPS的配对关系。
- `TimeServiceStatus`由PLATFORM Time Service唯一发布；M1/M2/M3/M4只读，不得自行维护第二份UTC offset/drift。
- `utc_uncertainty_ns`与ContractHeader的`event_time_uncertainty_us`含义不同，禁止互相代用。
- RTC/Companion/硬件同步源通过同一Time Service adapter注册独立clock domain；不得直接修改本地monotonic。
- 当前Flight产品固定`GNSS_SUPPORT=1`和`GNSS_PPS_CAPTURE=1`，GNSS/PPS生产路径始终创建；启动未获星、运动中失锁或PPS无脉冲时，Time Service仍提供本地monotonic，UTC/频率参考按实际质量报告。

### 4.3 编码、有效性与实例注册（首版唯一表）

所有跨模块struct只含显式宽度整数及IEEE754 float32/double64；自然对齐上限8，不使用pack或enum成员存储。小端ARM为本版参考ABI，网络/Flash必须字段序列化。保留字段写0；未知必需字段/bit/enum拒绝，padding不参与Hash。uint32诊断计数饱和到UINT32_MAX并设置溢出诊断；序列号按半范围比较且最大活跃间隔<2^31次。Epoch和execution_token非零、禁止回绕：耗尽后拒绝新授权并在地面维护重启；0只用于明确的未建立/非任务上下文。

| 注册项 | 固定值/规则 |
|---|---|
| profile_id | QUAD_X4=0x00010001；Host/SIL同契约、不同Manifest/build hash |
| frame_id | 0 UNSPECIFIED、1 LOCAL_NED、2 BODY_FRD、3 WGS84_GEODETIC；通用状态必须LOCAL_NED |
| clock domain | 0 FCU_MONOTONIC、1 UTC_POSIX、2 GNSS_GPS、0x1000 Companion；未注册域拒绝 |
| logical source_id | 1 RC、2 GCS、3 Companion、10 IMU、11 GNSS、12 Baro、13 Mag、20 M3、21 M4、22 M5、23 M6、24 M7、25 HEALTH、26 PLATFORM |
| sensor_instance_id/source mask | IMU=1/bit0、GNSS=2/bit1、Baro=3/bit2、Mag=4/bit3；扩展类型当前无源实例，不得假装已安装 |

所有消费者用原子ClockInstant确认boot/time与输入一致后才计算差；未来sample/publish时间不设置容差直接拒绝；UNCERTAINTY_BOUNDED缺失或年龄加误差超限拒绝。时间/float运算做溢出/有限值检查，不能用unsigned下溢获得“新鲜”。ERROR返回时所有out对象先置无效Header/mask，不沿用旧有效out；最后有效快照只能由独立get接口在原TTL内返回。

QUAD_X4固定24个未来点，`points[i].offset_us=(i+1)*20000us`，覆盖`t0+20ms..t0+480ms`；另有`anchor.offset_us=0`，因此可评估闭区间为`[t0,t0+480ms]`，不存在首20ms无锚点问题。t0取M5本次已复制导航快照的State Time，不能取任务开跑时间。point_count=24不含anchor。MPC仍为Np=20，不因增加anchor改变维数。

位置在相邻节点间唯一采用匹配两端p/v/a的五次Hermite插值，速度/加速度由同一多项式解析求导；yaw先按最小有符号角差连续展开（精确π按上次方向，否则取正方向），再用两端yaw/yaw-rate的三次Hermite插值，输出时wrap。插值系数和区间时长必须有限且正；禁止使用另一个不一致的线性插值器。M5-06验证的对象是这套实际发布/消费的分段曲线，不能仅验证发布前被重新采样的另一条曲线。原始最多8段quintic用于生成候选；重采样后anchor+24点产生24个消费插值区间，M5-06采用相同插值器对24区间验证，固定预算见04/07。

`t_mpc_eval=ControllerInput.control_time_us`，`t_k=t_mpc_eval+k*Ts+T_act`，k=1..20。当前反馈参考在control_time_us评估；T_act只移动未来参考预瞄，不能改变初始状态时刻。当前及全部Np参考必须处于可评估区间，不足则拒绝而不外推。M5以50Hz滚动发布，M6仅在完整输入bundle满足上述区间时使用；切换瞬间若最新State Time尚早于新t0，可保留仍获许可的旧bundle至下一有效快照，否则拒绝。

参考切换采用显式READY→Permit提交→ACTIVE确认：M5原子发布候选Reference和GuidanceStatus=READY；M4验证Feasibility、token、epoch/TTL后签发匹配的Permit，并立即通知M5/M6。READY+匹配有效Permit已表示可用参考，M6不等待M5下一次50Hz确认ACTIVE，避免循环等待。M5观察该Permit后发布ACTIVE。普通重规划且Directive/Authority未变时，旧bundle可在其原TTL内继续；撤销、模式/Authority/State变化立即使旧bundle失效，不能以旧参考掩盖撤销。M6入口由公共调用外壳复制/锁定一组相互匹配的不可变Reference/Status/Permit/Directive/Envelope，指针只覆盖同步调用；没有任何依据未定义任务先后顺序的相位假设。

Aerial payload 可为位置/速度/加速度/yaw/yaw-rate；UGV payload 可为路径弧长/横向误差参考/曲率/速度/纵向加速度/转向前馈；USV payload 可为位置/航向/surge-sway/yaw-rate 等。公共消息名和调用接口相同，但 payload 是编译期强类型，不能强迫所有车辆使用 XYZ+yaw。

M5 输出 `MotionReference`、`PilotControlReference`、`GuidanceStatus`、`GuidanceFeasibility` 和 `GuidanceHealth`。`MissionStatus`由M4 MissionManager唯一拥有和发布；M5只读取`AuthorizedMissionSnapshot`，不得生成、修改或发布MissionStatus。

QUAD授权快照的current_item_index必须小于waypoint_count且对应waypoint_id等于current_item_id；waypoint_id非零、任务内唯一。execution_token由M4在同一boot内严格递增且非零；新授权、换项、暂停后恢复/跳项/中止后的新执行都换token，溢出拒绝新执行。跨boot使用ContractHeader.boot_id区分，重启不自动恢复任务或解锁；旧结果即使mission_revision相同也不能推进。M4消费GuidanceStatus摘要签发Permit；轨迹过期、epoch/origin/profile/authority/directive不匹配必须拒绝，禁止静默外推。

### 11. M7：设备输出

M7许可接收、Demand接收和独立守卫分开：actuator_update_permit接收M4状态；actuator_apply只提交最新有效Demand，不直接发送硬件帧；actuator_poll由独立安全唤醒执行，即使无新Demand也检查所有有效期/心跳。NULL Demand不用于模拟idle；IDLE_ONLY由poll按产品策略生成。物理帧边界由驱动再次验证已准备帧的token、撤销watermark和截止时间；已开始的帧可完成其有界发送，撤销阻止后续帧，不能宣称撤回已发送命令。

### 12. Port API 生命周期

插件生命周期固定为 `validate(profile) -> init(config) -> update/push/poll -> stop`，`get_health`可在初始化后查询；init成功即进入RUNNING，没有隐含start函数。重复init在RUNNING返回STATUS_NOT_PERMITTED；stop幂等并清除有效输出。只有Estimator/Plant有下列显式reset函数，其他模块重置须stop后重新init。首版使用 C-compatible ABI 和编译期直接符号绑定：每个 Port 必须且只能链接一个实现；不使用动态库、反射、运行时扫描、RTTI 或堆分配。

- `FmsPolicyPort`：命令/能力/故障输入 → VehicleDirective/Permit/DecisionEvent。
- `EstimatorPort`：测量/时间质量/SensorUsePolicy → NavigationSnapshot/Capability/Reset/Health。
- `GuidancePort`：Directive/NavSnapshot/Mission/Environment → MotionReference/Feasibility/Status。
- `ControllerPort`：NavSnapshot/MotionReference/Directive/ActuatorStatus/ControlModel → ActuatorDemand/Capability/Health。
- `ActuatorPort`：ActuatorDemand/Permit → 设备输出/ActuatorStatus。
- `ControlModelPort`：固定维数预测/线性化/约束/适用域查询。
- `PlantSimulationPort`：Host/SIL/HIL Plant Truth 与 Sensor Truth；禁止用于实机闭环。

### 15. 版本与错误行为

本版使用 `CONTRACT_SCHEMA_MAJOR=6u`、`CONTRACT_SCHEMA_MINOR=0u`、`PRODUCT_CONTRACT_REVISION=0x00010906u`（QUAD_X4）和 `PORT_API_REVISION=0x00010906u`。消费者须重编译，并用本版生产头验证 Host/ARM ABI 锁。

所有跨模块数据必须校验 schema、profile、layout、epoch、validity、数据年龄和有限数值。版本不兼容、数据过期、profile 不匹配、未知 layout、NaN/Inf、队列溢出均返回明确错误并产生诊断证据；禁止静默使用旧数据或猜测字段语义。

```c
  LINK_FLAG_AUTHENTICATION_ERRORS = 1u << 3
};
/* ContractHeader.validity_flags carries RSSI/LQ/packet-loss field validity. */
typedef struct {
  ContractHeader header;
  uint32_t link_instance_id;
  uint16_t link_kind;          /* RC / GCS / COMPANION / OTHER: Product Contract */

```

Owner：M1。M4 消费。RSSI/LQ 不支持的链路使用 valid mask，不填伪造零值。`INTERFERENCE_SUSPECTED` 是证据标签，不是确定原因。恢复稳定性由 M1 报告，权限恢复由 M4 决定。

### 18. 诊断证据与车辆运动异常

模块只能发布本 ICD 已定义的公共证据类型：`SensorDiagnostic`（M2）、`EstimatorHealth`/`NavigationCapability`/`SensorConsistencyEvidence`（M3）、`ControlHealth`/`ControlCapability`（M6）、`ActuatorStatus`/`ActuatorHealth`/`ActuatorCapability`（M7）、`CommunicationLinkStatus`（M1）。`EstimatorDiagnostic`、单次观测门控结果及控制/执行器内部诊断记录属于所选插件的私有实现细节，不作为公共 ICD 类型或跨模块依赖。HEALTH 汇总公共健康/故障证据为 FaultSummary，不推断未经证实的物理原因。

如果需要跨模块事件索引，使用公共 envelope：

```c
typedef struct {

  uint32_t event_id;

  uint16_t evidence_class;      /* DIRECT/CORROBORATING/MODEL_BASED/UNKNOWN */
  uint32_t source_component_id;
```

该事件记录“观察到的事实”，不得把 `cause=wind/bird/sensor` 当作未经证实的真值。跨域证据的相关性由 M4 车辆策略结合 HEALTH 摘要解释；Sensor Integrity Manager 只对传感器源状态负责。

### 19. 健康状态语义

`SensorHealthState` 是源级状态；`SampleQuality` 是样本级质量；`NavigationCapability` 是导航能力；`EstimatorHealth` 是所选 EstimatorPort 的模块级健康快照；`ControlCapability` 和 `ActuatorCapability` 分别是控制/执行器能力。单次观测门控结果属于 EstimatorPort 私有实现，不是公共 ICD 类型。禁止复用同一 enum 或同一 bit 表示这些不同概念。

### 20. 有效期和权限

LinkStatus、OperatorInput、AuthorizedOperatorInput、VehicleDirective、ActuationPermit 均必须有 sample/publish time、valid_until 和 epoch。数据过期不能通过重新发布旧值来延长寿命。RC link 恢复不能自动增加 authority_epoch；只有 M4 授权转换才增加。

`ContractHeader.valid_until_us`只表示消息 envelope 新鲜度；领域对象使用明确命名的`*_expires_at_us`：OperationRequest=`execution_deadline_us`（业务完成截止）、VehicleDirective=`directive_expires_at_us`、ActuationPermit=`permit_expires_at_us`、ActuatorDemand=`demand_expires_at_us`、SensorUsePolicy=`policy_expires_at_us`、EnvironmentConstraint=`constraint_expires_at_us`、Home=`home_expires_at_us`、GuidanceStatus=`reference_expires_at_us`、AuthorizedMissionSnapshot=`mission_expires_at_us`。消费者采用 Header TTL 与领域有效期的较早者。不得再用相同`valid_until_us`字段名表达两种语义。


### 21. FMS Policy 调用输入/输出视图

`FmsPolicyPort`内部的MissionManager是MissionStatus唯一写入者。FmsInputView不再接收其自身MissionStatus；M4保存内部当前任务状态，通过FmsOutputView.mission_status发布。M1只提交完整、已校验传输的MissionUploadCandidate，不更新Mission状态。

### 22. 操作员权限接口方向

- M1 -> M4：`OperatorInput` + `CommunicationLinkStatus` + `OperationRequest`。
- M4 -> M5：`AuthorizedOperatorInput` + `VehicleDirective` + `AuthorityStatus`。
- M5 -> M6：根据`GuidanceStatus.reference_kind`提供且只提供一种有效参考：`MotionReference`或`PilotControlReference`；两者均携带匹配的Epoch/TTL。
- M4 -> M7：`ActuationPermit`。

M5/M6 不得旁路 M4 消费未经授权的原始 OperatorInput。RC 恢复不会自动产生新的 authority epoch；只有 FMS Policy 明确接受接管/模式转换时才更新。

## 2. 公共数据字典

<sub>来源文件：`03_公共数据字典.md`</sub>

### 1. 坐标、时间和单位

- 公共局部导航系 NED；航空机体系 FRD；四元数 `[w,x,y,z]` 表示 body-FRD 到 nav-NED。UGV/USV 使用产品合同定义的车体/船体坐标，但转换必须显式。
- 区分 sample time、hardware capture time、DMA complete、task consume、publish/receive time。估计和控制使用采样时间；其他时间只用于延迟诊断。
- 外部时钟携带clock domain、mapping epoch和uncertainty；外部源重置增加其mapping_epoch，本地连续性中断才增加time_epoch。
- 单位：m、m/s、m/s²、rad、rad/s、N、N·m、kg、kg·m²、µs。禁止无单位 float。

### 2. 五种不同的有效性/健康概念

| 概念 | 表达什么 | 典型 Owner |
|---|---|---|
| Field Validity | 字段是否存在、当前是否可用 | 消息生产者 |
| Sample Quality | 当前测量样本是否完整、及时、未饱和 | M2 |
| Device Health | 设备/驱动本体状态 | Driver/BSP、M2 |
| Measurement Consistency | 观测是否与预测/其他观测一致 | M3 |
| Navigation Capability | 导航状态是否足以支持某类任务 | M3 |
| Vehicle/Control Capability | 车辆当前还能安全实现哪些控制自由度 | M6/M7 |

`valid_mask` 不能代替不确定度；设备健康不能代替样本有效性；样本有效不代表观测一定符合运动模型；导航有效不代表车辆可控。

### 3. 传感器健康状态

源级状态：`UNKNOWN`、`INITIALIZING`、`HEALTHY`、`SUSPECT`、`DEGRADED`、`QUARANTINED`、`FAILED`、`RECOVERY_PROBATION`。

样本级质量：`VALID`、`DEGRADED`、`INVALID`、`UNSYNCHRONIZED`、`STALE`。单个样本质量变化不得直接重写源级状态。

估计器观测处理：`ACCEPTED`、`REJECTED_OUTLIER`、`REJECTED_INVALID`、`DELAYED_FUSED`、`TOO_OLD`、`NOT_FUSED`。

导航解状态：`INITIALIZING`、`VALID`、`DEGRADED`、`INVALID`，并用 capability mask 描述可用位置/速度/航向/高度/姿态等能力。

### 4. 车辆异常分类

- `SENSOR_DEVICE_FAULT`：设备自检/总线/供电/硬件故障证据。
- `SAMPLE_INTEGRITY_FAULT`：CRC、序号、冻结、饱和、时间或数据完整性异常。
- `MEASUREMENT_INCONSISTENCY`：观测与预测/其他来源不一致，原因未定。
- `NAVIGATION_DEGRADATION`：状态/协方差/可观性导致能力下降。
- `UNEXPECTED_MOTION`：车辆真实运动与参考或模型预测偏离，原因未定。
- `EXTERNAL_DISTURBANCE_SUSPECTED`：风、流、碰撞、鸟撞等外部作用的证据；不等于已识别具体原因。
- `MODEL_MISMATCH`：预测模型与实测动态持续不一致。
- `CONTROL_LIMITATION`：控制输出达到约束/饱和或控制能力不足。
- `ACTUATOR_FAULT`：电机/舵机/推进器反馈或输出异常。
- `LINK_DEGRADED/LINK_LOST`：通信链路质量下降/丢失。

不得把 `MEASUREMENT_INCONSISTENCY` 自动映射为 `SENSOR_DEVICE_FAULT`。

### 5. 权限与命令状态

- Link state：`UNKNOWN/INITIALIZING/HEALTHY/DEGRADED/LOST/RECOVERING`。
- QUAD Authority仅为NONE/PILOT/MISSION/GCS_SUPERVISED；Companion为ADVISORY，SAFETY为强制约束。其他产品的来源枚举由各自Product Contract定义。
- Authority transition 必须增加 `authority_epoch`；过期/旧 epoch 命令拒绝。
- `LINK_RECOVERED`、`OPERATOR_TAKEOVER`、`AUTO_RESUME` 是三个不同事件。

### 6. 模型和参数标识

`product_profile_id`、`nav_layout_id`、`motion_reference_layout_id`、`control_layout_id`、`actuator_layout_id`、`model_id/version/hash`、`parameter_set_id/hash` 在构建 Manifest 中固定。跨域模型不能仅凭同一个名称视为同一模型。

### 7. 配置术语

- Tuning Parameter：四份CORE源文件中的模型/外参/噪声/控制整定值；修改后重编译。安全阈值/超时不是普通调参，归受控策略。
- Vehicle Model Parameter：质量、惯量、阻尼、几何和执行器效能等模型参数。
- Calibration Data：doc/calibration/保存原始证据；最终生效外参/模型只进入四份CORE源文件并随固件构建，不构成第二份运行时来源。
- Build-time Constant：维数、缓冲容量、最大执行器数、预测步数等影响内存布局的编译期常量。
- Safety Policy Parameter：FMS 安全阈值和操作策略；修改需独立安全审查。

### 8. 时间质量与GNSS信号丢失状态（V1.9.1现行）

#### 时间状态（TimeQuality）

`LOCAL_ONLY`、`ACQUIRING`、`LOCKED`、`HOLDOVER`、`DEGRADED`、`INVALID`。LOCAL_ONLY表示本地单调时间有效但没有可信外部UTC映射；只有本地时钟本身不可靠才是INVALID。

#### 时间字段语义

- `clock_domain_id`：本地单调时钟域。
- `time_epoch`：本地时钟连续性epoch；重启/计数器复位/无法证明连续的时钟切换后变化。
- `mapping_epoch`：外部UTC/设备时钟映射epoch；无映射为0。
- `timestamp_sample_us`：FCU monotonic sample time，绝不存UTC。
- `event_time_uncertainty_us`：物理sample event映射到FCU monotonic的误差。
- `utc_uncertainty_ns`：仅由TimeServiceStatus报告，描述UTC映射误差。

#### GNSS状态必须拆分

当前必装GNSS产品不允许以`GNSS_NOT_INSTALLED`掩盖故障。`GNSS_NAV_LOST`（导航观测不可用）、`PPS_LOST`（时间参考边沿丢失）、`UTC_EPOCH_INVALID`（无可信绝对时间历元）、`TIME_MAPPING_DEGRADED`（外部映射误差超限）、`TIME_BASE_FAULT`（本地时钟本身异常）不得互相替代。

## 3. 编译期可插拔架构与 Port 边界

<sub>来源文件：`31_统一接口与编译期可插拔架构规范.md`</sub>

### 1. 本文件的核心决议

**公共 Port 由各模块的构建配置静态绑定到唯一兼容实现。** 开发者适配所需的 FMS、控制及 Plant，并验证它们与目标数据契约匹配。

公共 Port 的名称、生命周期、输入输出语义和错误规则稳定。车辆差异通过 `product_contract.h` 提供强类型 payload，同一目标的所有模块共用一个 Product Contract。网络和文件协议分别定义独立序列化格式。

### 2. 依赖方向

```text
Module build configuration and Host plant binding
       | bind one compatible implementation per Port
       v
M1-M7 common modules -> stable Port/ICD -> selected implementation
       |                                  |
       +---------- shared services -------+

Platform boundary: RT-Thread 5.3.0 native Device Framework/BSP
Host boundary: PlantSimulationPort/SensorSimulationPort (SIL/HIL only)
```

调用方只依赖 Port 和 ICD；实现只依赖 Port/ICD 和本领域配置；公共接口不依赖车辆实现、RT-Thread 私有头、HAL 或 Simulink 生成类型。禁止实现之间互相调用私有函数。

### 3. 不同插拔点

| Port | 语义 | Owner | 选项 |
|---|---|---|---|
| FmsPolicyPort | 操作状态机/命令仲裁/安全决策 | M4 | Aerial/Ground/Marine 完整策略 |
| EstimatorPort | 测量→导航状态/能力 | M3 | KF-GINS_QUAD（首版）/UKF（其他Profile候选） |
| GuidancePort | Directive+Nav→运动参考 | M5 | Aerial/UGV/USV |
| ControllerPort | Nav+Reference+Constraints→ActuatorDemand | M6 | 各车辆完整控制 pipeline |
| ControlModelPort | 预测/线性化/约束/适用域 | M6 | LTI/LTV/LPV/有界非线性，按车辆 |
| ActuatorPort | 物理需求→设备命令/反馈 | M7 | Motor/Steering/Thruster |
| PlantSimulationPort | 物理被控对象仿真 | Host/SIL/HIL | Quad/UGV/USV Plant |
| SensorSimulationPort | PlantTruth→模拟传感器测量 | Host/SIL/HIL | 各车辆传感器模型 |

### 4. FMS：完整车辆策略，不做万能状态机

`FmsPolicyPort` 的统一调用流程为 `fms_policy_validate -> fms_policy_init -> fms_policy_update -> fms_policy_get_health -> fms_policy_stop`（M4无reset/start接口）。各产品的 OperationRequest/Directive payload 在 Product Contract 中强类型定义。Aerial FMS 自己定义 arming/takeoff/flight/RTL/land 状态；UGV 自己定义 drive/route/park/stop；USV 自己定义 propulsion/loiter/return/dock。公共层不强迫共享这些状态节点。

共用的只是命令 envelope、授权元数据、有效期、DecisionEvent 和基础安全校验。FMS 不访问 Estimator/MPC 私有状态，不负责源级传感器隔离。

### 5. Estimator：导航估计算法整体替换

`EstimatorPort` 固定为测量输入、时间质量和SensorUsePolicy，输出NavigationSnapshot、NavigationCapability、StateResetEvent、EstimatorHealth。内部名义状态、21/22维误差状态、协方差矩阵布局、观测模型和延迟历史不外泄。QUAD_X4首版绑定KF-GINS_QUAD；其他Profile可选择符合公共状态语义、时间/质量要求和实时预算的估计器。KF-GINS适配细节唯一见05号文档。

车辆运动约束/测量模型默认是 Estimator 插件内部实现，不为每个内部数学函数再造公开 Port。

### 6. Guidance：车辆专用运动参考

`GuidancePort` 固定生命周期和消息 envelope。MotionReference 的公共元数据统一，轨迹点 payload 由 Product Contract 强类型选择。Aerial 不强迫 UGV/USV 使用 XYZ+Yaw；UGV/USV 不污染 Aerial 字段。M6 只消费当前产品类型的参考。

### 7. Controller：完整闭环控制 pipeline

`ControllerPort` 输入 NavigationSnapshot、MotionReference、VehicleDirective/SafetyEnvelope、ActuatorCapability/Status、ControlModel View 和 now。输出 Product-typed ActuatorDemand、ControlCapability、ControlHealth。

M6 内部可分控制律、控制模型、allocator，但它们是该 Controller Pipeline 的内部实现；除 ControlModelPort 这一真实独立替换点外，不把每个环节都变成运行时插件。QUAD 可使用 MPC→推力映射→SO(3)→Rate PID→X4 allocator；UGV/USV 使用各自拓扑。

### 8. 模型分离

- Estimator Model：M3 私有。
- Control Prediction Model：M6 的独立 ControlModelPort。
- Plant Simulation Model：Host/SIL/HIL only。
- ActuationEffectivenessData：M6 allocator 使用。
- ActuatorCalibrationMap：M7 使用。
- ActuatorDynamics：Plant Simulation Model 使用。

不建立一个万能 `ActuatorModelOps` 同时负责效能矩阵、逆映射、动态和设备命令。

### 9. C ABI 和强类型 Product Contract

目标采用 C-compatible 头文件和函数符号静态绑定。公共函数名固定，例如 `fms_policy_update`、`estimator_update`、`guidance_update`、`controller_update`、`actuator_apply`。具体实现编译时提供同名符号。一个目标缺失或重复实现必须 link fail。

`product_contract.h` 定义 `ProductNavExtension`、`ProductOperationPayload`、`ProductOperatorInput`、`ProductFmsInputExtension`、`ProductDirectivePayload`、`ProductSafetyEnvelopePayload`、`ProductPilotControlReferencePayload`、`ProductMotionPoint`、`ProductActuatorDemand`、`ProductActuatorFeedback`、`ProductActuatorCapability` 和 `PRODUCT_MAX_PENDING_OPERATION_REQUESTS`。QUAD、UGV、USV 各自的目标契约定义 `ProductSafetyEnvelopePayload` 和 `ProductPilotControlReferencePayload`。公共消息头先包含目标契约，再声明 `SafetyEnvelope` 和 `PilotControlReference`。跨模块数据使用强类型，模块私有配置可以通过强类型 private view 传递，指针仅在同步调用期有效。

不要求不同产品之间的内存 ABI 完全相同；要求同一产品所有模块的 ABI/schema/layout hash 完全一致。外部 wire protocol 有独立 schema。

### 10. Product Profile 兼容矩阵

每个目标使用唯一的产品契约。开发者在各模块配置中选择并适配实现，Manifest 记录契约、平台、所用实现、传感器、坐标系、布局和模型及参数 hash。CI 检查车型、状态及参考布局、控制及执行器布局、坐标系、采样、资源预算和能力兼容性。

### 11. 传感器故障职责

Driver/BSP 报硬件和 DMA 证据；M2 做样本质量；M3 做观测级创新门控；Sensor Integrity Manager（HEALTH 子服务）拥有源级隔离/恢复；M3 消费 SensorUsePolicy；M4 决定操作响应。M6/M7 分别拥有控制/执行器本地诊断。不得有两个模块维护同一隔离状态机。

### 12. RT-Thread 决议

只使用 RT-Thread 5.3.0 原生 Device Framework、原生总线/设备子框架、BSP、IPC、Timer、DMA/IRQ 机制。禁止第二套 DeviceInstance/DeviceDriverOps/DriverManager。高频 DMA/FIFO 实现在具体原生 RT-Thread driver 内部；M2/M7 通过原生设备接口和薄的强类型适配层访问。

### 13. Simulink

Simulink Plant 通过 PlantSimulationPort；Simulink 线性化/控制预测模型通过 ControlModelPort Adapter；生成控制代码通过 ControllerPort Adapter。固定步长、固定维数、无动态内存，代码生成模型和参数必须版本化。PlantTruth 不进入闭环。

### 14. CI 门禁

- 每个 Port 恰好一个实现；零/多实现 fail。
- Product Profile 和插件兼容矩阵通过。
- 结构体 size/alignment/offset、ABI/schema/layout hash 检查。
- 公共核心无车辆私有 include、无 RTOS/HAL/Simulink 依赖。
- 替换 FMS/Estimator/Guidance/Controller/ControlModel/Actuator 实现时公共消费者不修改。
- H723 固定内存、无高频 malloc、WCET/RAM/stack 实测。
- SIL/HIL、模型 golden vectors、故障注入通过。

### V1.8 补充：运行时事实与策略分离

Port 不仅要定义函数签名，还必须定义“事实输入”和“决策输出”的边界：M1 发布 LinkStatus/OperatorInput，M4 输出 AuthorizedOperatorInput/AuthorityStatus；M2 发布 SensorDiagnostic，Sensor Integrity Manager 发布 SensorUsePolicy；M3对外发布NavigationSnapshot、NavigationCapability、EstimatorHealth和恢复专用SensorConsistencyEvidence；后者仅供Sensor Integrity使用，内部矩阵/逐次残差不进入公共ICD；M6/M7 分别发布 ControlCapability/ControlHealth 与 ActuatorStatus/Capability，M4 决定操作响应。插件不能越权修改其他模块的状态。

工程师可调的模型/导航噪声/控制增益通过精简 `config/` 提供；FMS/FDIR/链路安全策略由车辆专用实现和受控安全契约管理。Port 不暴露任意参数写接口；运行时参数更新不是插件生命周期的一部分。

### GNSS作为必装主要器件与运行期质量门控

QUAD_X4固定接入UM982及PPS：`GNSS_SUPPORT=1`、`GNSS_PPS_CAPTURE=1`，BSP必须包含UART4 RX DMA、TIM2_CH3和对应IRQ/缓冲；禁用任一项为配置错误。GNSS位置/速度是主要外部导航观测，但每个观测仍必须通过时间、Fix、协方差和一致性门控。GNSS/PPS信号可丢失，驱动及健康监控持续存在，不能因此改变编译配置或设备Owner。

公共消费者使用NavigationCapability、TimeServiceStatus和有效数据源；本地单调时钟/IMU传播不等待Fix或PPS。当前产品不提供裁剪GNSS的固件Profile；CI改测信号丢失与恢复，以及必需UART/DMA/PPS配置的负向检查。其他车辆的硬件组合须另有明确产品需求，不改变本Flight基线。


## 4. Product Contract 强类型样例与静态绑定

本版冻结QUAD_X4的完整类型和调用契约；UGV_BICYCLE、USV_3DOF段仅作非规范性设计草案，不属于当前可构建Profile，也不得声称Host ABI兼容已验收。增加其他产品需独立完整类型/资源/测试后再接纳。参数实测值与接口定义分开：缺实测值阻止对应硬件能力启用，不允许缺类型。

### 1. 统一原则

所有产品共用 `ContractHeader`、ICD 中定义的 `NavStateCore`/`NavigationSnapshot`、NavigationCapability、Port 函数名和生命周期。每个目标的 `product_contract.h` 定义以下强类型。

- `ProductNavExtension`
- `ProductHomeTargetSnapshot`（QUAD FMS directive payload）
- `ProductObstacleObservation`（QUAD M2→M5 environment input）
- `ProductOperationPayload`
- `ProductDirectivePayload`
- `ProductMotionPoint`
- `ProductActuatorDemand`
- `ProductActuatorFeedback`
- `ProductActuatorCapability`
- `ProductSensorMeasurement`（非 IMU 异步测量的强类型 tagged union）
- `ProductMissionPayload`、`ProductEnvironmentConstraint`
- `ProductFmsConfigPayload`、`ProductEstimatorConfigPayload`、`ProductGuidanceConfigPayload`、`ProductControllerConfigPayload`、`ProductActuatorConfigPayload`
- `ProductPlantInitialState`、`ProductPlantTruth`、`ProductEnvironmentState`
- `PRODUCT_MAX_SIM_MEASUREMENTS`
- `PRODUCT_PREVIEW_COUNT` 和控制模型 NX/NU 等编译期维数

不使用 `void*`、未定义单位数组或运行时反射。配置 payload 必须在所选 Product Contract 中用强类型完整定义单位、范围、默认值和版本；不得把参数隐藏在无类型 blob 中。跨产品内存布局不要求相同；同一产品内必须 ABI 一致。

`ProductObstacleObservation` 语义约束：`observation_id` 对 `OCCUPIED_PRIMITIVE` 表示障碍物跟踪身份，必须在同一 `sensor_instance_id` 内对同一目标的连续观测保持稳定，不得作为逐帧序号；`(sensor_instance_id, observation_id)` 唯一标识一个活动目标，源端不得在其有效期内复用。`FREE_SPACE_RAY` 的 `observation_id` 标识单条射线观测，可逐条变化。若源端不能提供稳定目标身份，必须先在 M2 完成目标关联，再发布动态障碍；M5 不做未经验证的最近邻关联。`sensor_instance_id` 是完整32位源身份，M5 跟踪表不得截断。`confidence_0_to_1` 是来源质量分数，不得直接解释为经校准的碰撞概率；`position_std_m/velocity_std_mps` 是观测不确定度输入，必须结合经验证的产品级保守膨胀系数形成碰撞检查包络。`source_health=REJECT`、无效/过期 Header、Origin/State Epoch 不匹配、非有限数值或未支持的 shape/kind 必须拒收；UNKNOWN/STALE/INVALID/地图外空间不得按 FREE 处理。动态障碍预测只在观测有效期和产品批准的预测窗口内有效，超过窗口后按未知/保守占据处理。

### 4.1 ProductSensorMeasurement 约定

`ProductSensorMeasurement` 是 tagged union，只包含当前产品启用的异步观测类型，例如 GNSS、Baro、Mag、Range、Flow、WheelOdometry、Airspeed 或 WaterSpeed。每个 union 成员本身仍是独立强类型结构，含单位、sample time、sensor ID、calibration version 和 quality flags。高频 IMU 不进入该 union，使用独立 `ImuSample` 快速路径。这样不会用一个无语义 float 数组承载不同测量。

M2→M5观测通道由M5公共外壳从固定ring非阻塞取出最多8条只读观测注入GuidanceInput；调用后释放原始观测槽，M5-02复制到自己的固定地图/track内存，不保存输入指针。NONE模式observation_count必须为0；超限返回STATUS_BUFFER_FULL，队列过载只降级地图，不能反压IMU。

ActuatorCommitReceipt由M7唯一发布。PLATFORM驱动仅报告真实提交序号/时刻/驱动结果，M7补齐许可上下文和经标定映射可还原的命令等效物理需求。M6在固定8项历史中用applied_control_sequence匹配曾发布请求，再计算命令级抗饱和残差；不要求它等于当前最新sequence。Receipt TTL为10ms设计上限，跨epoch/无匹配记录/过期则忽略附加反馈；主anti-windup仍使用allocator估计残差。ESC反馈NONE不影响Receipt存在，但Receipt绝不是RPM/实测力。

`MissionStatus`、`GuidanceFeasibility`、`GuidanceStatus`、`FmsStateSnapshot`、`PreArmCheckResult`、`PilotControlReference`、`CommandAck`、`DecisionEvent` 和 `ModuleHealth` 的公共字段在 02 ICD 中定义。领域健康结构以 `ModuleHealth` 为公共前缀并在 ICD 中追加固定字段；不得由实现各自定义同名不同义版本。

首版 ProductProfile 的 `profile_id` 为 `0x00010001`。操作员输入、导航、运动参考、执行器的布局 ID 依次为 `0x1001`、`0x1002`、`0x1003`、`0x1004`，ControlModelDescriptor 使用 `0x2001` 和 `0x2002`。实现 ID 对应各模块实际绑定的实现，首版 FMS、Estimator、Guidance、Controller、ControlModel 和 Actuator 分别为 `0x1101`、`0x1201`、`0x1301`、`0x1401`、`0x1501` 和 `0x1601`。替换实现应维护对应 ID，产品和 ABI SHA256 须精确匹配。

单位与界：初始P按上三角row-major(i=0..21,j=i..21)253个double序列，状态单位按05；ARW rad/sqrt(s)、VRW m/s/sqrt(s)，bias gyro rad/s、accel m/s²、scale无量纲，相关时间s且>0，baro bias谱密度m²/s；位置/速度/观测floor是标准差而非方差。Controller J kg·m²，SO3 gain s⁻¹，Kp N·m·s/rad、Ki N·m/rad、Kd N·m·s²/rad、Kaw s⁻¹，积分上限N·m；位置PD kp s⁻²、kd s⁻¹；MPC权重对04的归一化变量定义、无量纲，Q/Qf/S非负且R严格正。M3端所有variance是平方单位、有限且>0。

当前硬件组合包括IMU和主要必装UM982，GNSS位置/速度为主要外部观测；未获Fix、解析/时间或质量证据不足时相关导航能力必须保持NOT_READY/无效，不以固定安装推定已经有效融合。Baro/Mag/Range/Flow按各自接纳证据提供能力。boot_id由平台经已验证HWRNG生成非零64bit（board UID区分设备），RNG失败输出NOT_READY并抑制控制；不能用每次相同UID/0启动时间作为新会话。初始epoch为1；首次采集早于pipeline修正或缺少前一有效样本时不发布可传播IMU。stop幂等，stop后update返回NOT_READY，重新init必须先validate，输出缓冲在错误返回时全部标记invalid。


ALT_HOLD固定采用GuidanceStatus.reference_kind=GUIDANCE_REFERENCE_ALTITUDE_PILOT，PilotControlReference.reference_kind=PILOT_REFERENCE_ALTITUDE_ATTITUDE。valid_mask必须含ATTITUDE、ALTITUDE_UP、VERTICAL_VELOCITY_UP；RATE/THROTTLE位清零。M5在模式进入时从Nav锁存h_sp=-p_D，之后按实际State Time间隔积分v_up_sp=(2*throttle_norm-1)*垂向速度上限；同时按04人工姿态规则生成q_desired。高度参考必须在包线内且匹配Origin/state，不要求水平位置；切换/reset重新锁存，不能沿用旧h_sp。M6据此只求垂向PD和姿态/Rate PID，不能把它强制送入完整XYZ MPC。

Header注册表中ModuleHealth的C别名FmsHealth/GuidanceHealth/ActuatorHealth复用41，由component_id区分；EstimatorHealth和ControlHealth以common.header为首层头，显式消息ID54/55（见JSON），类型嵌套不能使其漏注册。TimeServiceStatus等不含ContractHeader的平台服务结构不是MessageBus消息ID，不猜测补Header。消息编号在Schema6内只追加，已分配值不随段落移动。

此类型由四份CORE中的sensor_alignment.yaml生成到.rodata供M2读取，不增加运行时设备框架。R须RᵀR≈I/det>0、soft-iron有限可逆、scale分母远离0、delay非负且在07预算内；未verified的源不发布CALIBRATED/时间有效位。M2先做传感器出厂补偿，再按本配置零偏/比例和安装旋转校正；M3的bg/ba/sg/sa为校正后剩余误差，初值与先验不得把同一静态校准重复扣除。

M3 WGS-84机械编排所需初始LLH由ProductEstimatorConfigPayload提供：可来自地面录入的已知地点或经验证GNSS初始化，启动未获Fix或运行中GNSS暂时丢失不阻止使用前者。没有有效地理锚点时IMU采集/时钟照常运行，导航保持INITIALIZING/NOT_READY，不假定纬度零来声明可控状态。Host fixture可显式选(0°,0°,0m)，标为SIM_ONLY。initial_origin_valid_mask的WGS84位与经确认的来源共同生效，local_radius_limit>0；磁D/方差/水平场下界只有aiding_mask含MAG时必填。初始P含bg/ba/sg/sa等23名义量对应的22误差分量，q不直接作为4维误差。

Nav与NavigationCapability每次作为同一发布世代生成：Header.sequence、sample_time、boot/time/state/origin必须一致，能力所据标准差来自该Nav；消费者不把旧Capability与新Nav拼接。Origin快照可以低频，但其origin/state必须匹配且TTL有效。尚无M3状态时不生成valid能力。


### Raw SPI字节序、补充字段与C链接规则

ADIS驱动在SPI16bit/MSB-first模式以uint16_t=0x6800发送命令。驱动私有 DMA RX 为 CPU 小端 word 镜像：34B共17个LE uint16，第0字为命令期间dummy（忽略），第1 DIAG_STAT，之后按gyro X LOW/OUT、Y LOW/OUT、Z LOW/OUT、accel X/Y/Z LOW/OUT、TEMP、DATA_CNTR、checksum排列。32bit测量bits=(uint32(OUT)<<16)|LOW，再按二补码解释为int32；禁止把总线MSB顺序直接当CPU byte数组再次换序。checksum对响应前30字节求和（字节顺序不影响和），不含第0 dummy与checksum。DATA_CNTR为16bit，每次输出更新加1并回绕；M2有界扩展为逻辑uint32 sample_sequence，gap/重启明确记录，不能把wrap误当reset。

TimerCaptureEvent.flags：bit0 CAPTURE_VALID、1 OVERCAPTURE、2 OVERFLOW_AMBIGUOUS；后两位出现不能提交有效样本。IMU 驱动发布已接收记录并标记 `IMU_FLAG_VALID`，传输异常置 `IMU_FLAG_TRANSPORT_ERROR`。驱动统计校验和错误，M2 按传输状态和 burst 校验结果拒绝无效采集。

GuidanceFeasibility.violated_constraint_id：0 NONE、1 DYNAMICS、2 SPEED、3 ACCELERATION、4 JERK、5 TILT、6 THRUST、7 GEOFENCE、8 COLLISION、9 TIME、10 CAPACITY；无法证明的最早违反offset取0（立即保守拒绝），不冒称知道未来真实碰撞时刻。ControlHealth/MpcOutputSnapshot/FCU_CONTROL_STATUS的solver_status归一化为0 NOT_RUN、1 SOLVED、2 SOLVED_INACCURATE、3 MAX_ITER、4 PRIMAL_INFEASIBLE、5 DUAL_INFEASIBLE、6 NUMERICAL_FAILURE、7 DEADLINE_EXCEEDED、8 INVALID_INPUT；与OSQP原生枚举显式映射。1/2仍须满足04残差及独立约束检查。

各消息检查自己固定frame，而不是要求bundle中所有frame相等：Nav/Capability/Origin/Motion/PilotReference/Geofence/Obstacle为NED(1)，Imu/Mag为FRD(2)，Gnss为WGS84(3，其速度字段仍显式NED)，Baro压力高度和授权/状态/推力通道消息为UNSPECIFIED(0，单位由字段定义)。SensorMeasurement外层frame跟活动payload一致。局部几何还必须校验同Origin/state；frame码不替代原点身份。

ProductProfile.nav_layout_id=0x1002、motion_reference_layout_id=0x1003、actuator_layout_id=0x1004；OperatorInput.input_layout_id=0x1001。ControlModelDescriptor用独立state_layout_id=0x2001（pN/E/D、vN/E/D六状态）、input_layout_id=0x2002（aN/E/D三输入），model_kind=1LTI/2LTV/3LPV/4NONLINEAR，首版1。矩阵row-major，首版A=[I TsI;0 I]、B=[0.5Ts²I;TsI]、c=0。不得把Operator四通道layout当成模型加速度input layout。

ProductFmsConfig.verified_input_mask采用PreArm ID bit0..14；所有超过模式所需的未验证位保持0。Actuator curve_count每电机2..16、thrust严格递增、DShot code单调；驱动普通推力只允许0（stop）或48..2047，不允许把1..47特殊命令当油门。高于curve_count的表项清零，motor_timer_permutation必须为0..3置换。

公共头自包含<stdint.h>/<stddef.h>，函数原型在C++下必须置于`extern "C" { ... }`中（使用__cplusplus条件保护），实现导出同一C链接符号；类型/宏不靠未声明的HAL/RTOS头补定义。规范ARM夹具按相同规则编译；生产头及C/C++混合链接仍需未来真实构建验收。

QUAD公共NavStateCore的position/velocity/acceleration参考点固定为机体重心CG，姿态仍body-FRD→NED；惯量、旋翼位置及Host Plant位置也以CG为原点。KF-GINS内部名义LLH仍是IMU测量中心，M3按05受控杆臂转换后发布CG状态/不确定度。公共加速度无可信角加速度/杆臂补偿时清ACCELERATION有效位并写零，不把IMU比力或IMU中心加速度冒称CG加速度。

模块stop/init只允许DISARMED维护流程。Composition Root先请M4撤销Permit/参考并确认输出抑制，再停算法；当前boot内所有epoch/token高水位保存在所属外壳，重新init不能清零复用。不能保留高水位的全图重启必须重建平台boot_id并清全部队列，禁止局部重启后接纳旧授权。


### 2026-11-05 M4/M5 实施接口增量（CR-V191-M45-01）

该实施增量将 QUAD Product/Port Revision 由 0x00010904 升至 0x00010905，Schema 为 6.0。

`ProductDirectivePayload.target_valid_mask`：bit0=POSITION，bit1=YAW，其余保留为0。POSITION有效时`target_position_ned_m[3]`为当前Directive state_epoch / Nav origin的Local NED、米；YAW有效时`target_yaw_rad`为弧度。零mask表示由授权当前任务项、Home或锁存保持点推导目标。M4是唯一写入者；TAKEOFF经Home与完整位置能力验证后发布HOLD/TRAJECTORY和明确起飞目标，任何目标变更增加directive_epoch。M5不得把失效/非有限目标替换为当前位置成功发布。

`ProductGuidanceConfigPayload.mass_kg/gravity_mps2`是动力学可行性所需的模型视图，必须来自与M6/Host Plant相同的vehicle_model数据，严格正且有限；不能从推力上限反推。默认辅助函数只提供1kg、9.80665m/s²的Host合成夹具，不能作为实机标定。M5用`m*||g*eD-a||`和推力方向检查推力/倾角界。

H723/NONE实现单段固定端点minimum-jerk quintic，采用0.2s时格、最多16次、总时长不超过6.2s；实际消费24个Hermite区间逐段验证。源到期时间的最小值限制Reference/Status/Feasibility；Header.sample保持导航State Time，publish使用evaluation_time。未接纳的STATIC_MAP/SIMULATION/ONBOARD模式在init拒绝，不生成空地图或避障成功声明。

自动垂向着陆：M4在水平导航不满足或Home失效时显式选择LAND/ALT_HOLD，M5仅消费有限的垂向位置/速度、姿态/角速度及包线，发布GuidanceReferenceKind=5，不填写虚构的XYZ MotionReference。以最多1m的连续五次下降段逐步下降，有效Home存在则截至Home高度；可靠LANDED证据成立则保持。该路径没有水平导航保证，存在需证明的围栏时拒绝；M6必须识别该显式类型并只使用垂向控制及姿态/Rate环，未知类型一律拒绝。它不授予Pilot Authority，自动任务token保持0。

围栏初始化配置：`fms_configure_product_geofence`在调用内验证并复制几何到M4已分配的独占存储，调用返回后原配置即可失效。下一次init消费安装标志（成功/失败均消费），重试须重新安装；init仅保留围栏区并清理其他引擎状态，不创建第二份全局配置或完整围栏栈副本。stop清除待安装状态。
